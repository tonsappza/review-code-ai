## Summary

PR นี้เพิ่มข้อมูลคำขอธนาคาร (เลขที่คำขอ / พฤติการณ์) ใน Bank Upload list และ detail โดยดึงจาก `FormRequestBank` เมื่อมี `FormRequestBankID` และแก้ Cassandra mapping ด้วย `ExplicitColumns()` + `[Ignore]` บน `RequestNo` เพื่อไม่ให้ query คอลัมน์ที่ไม่มีในตาราง — ทิศทางถูกต้องและสอดคล้องกับ `PhoneUploadService` ที่มีอยู่แล้ว

จุดที่ควรแก้ก่อน merge คือ **performance ของ list endpoint** (query ซ้ำต่อแถว) และการ **ซ่อน error ทั้งหมด** ใน helper ใหม่ ส่วนการเพิ่ม field ใน response เป็น additive contract ไม่ breaking

## Findings

### [major] — N+1 Cassandra queries ใน list (ซ้ำ 2 ครั้งต่อแถว)
- **File:** `bigdataAPI/Services/SP_BankUploadService.cs` (ประมาณบรรทัด 321–332, 1169–1207)
- **Issue:** หลัง paginate แล้ว loop แต่ละ `BankUpload` เรียก `GetBookNumberByFormRequestBankID` และ `GetCircumstanceByFormRequestBankID` แยกกัน แต่ละตัวสร้าง `FormRequestBankRepository` ใหม่และเรียก `GetFormRequestBankByRequestBankID` (มี `AllowFiltering`) — ได้ **2 query ต่อแถวในหน้าเดียว** (เช่น page size 20 ≈ 40 round-trips) ทำให้ list ช้าลงและโหลด Cassandra สูง
- **Suggestion:** รวมเป็น helper เดียวที่คืน `(BookNumber, Circumstance)` จาก list เดียว หรือ preload เป็น `Dictionary<Guid, FormRequestBank>` จาก `FormRequestBankID` ที่ไม่ซ้ำในหน้านั้นก่อน map response (pattern เดียวกับที่ควรทำใน Phone upload ถ้ายังไม่ได้ทำ)

### [minor] — `RequestNo` บน entity ไม่เคย hydrate จาก DB
- **File:** `bigdataAPI/Models/Entity/SP_BankUploadModel.cs` (บรรทัด 51–52), `bigdataAPI/Services/SP_BankUploadService.cs` (บรรทัด 323, 375)
- **Issue:** `RequestNo` ถูก `[Ignore]` และไม่มี column mapping — ค่าจาก Cassandra จึงเป็น `null` เสมอ ทำให้ `bookNumber = x.RequestNo` และ fallback `bookNumber ?? x.RequestNo` ไม่มีผลจริง ทุกแถวที่มี `FormRequestBankID` จะไป lookup repository เสมอ (ไม่ผิด logic แต่ทำให้เข้าใจผิดว่ามี denormalized `request_no` ใน `bank_upload`)
- **Suggestion:** ลบ property/branch ที่ไม่ใช้ หรือ persist/map `request_no` จริงถ้ามีแผน denormalize; ไม่งั้นใช้ `FormRequestBankID` เป็นเงื่อนไขเดียวและตั้งชื่อตัวแปรเป็น `bookNumber` ตั้งแต่ต้น

### [minor] — กลืน exception โดยไม่ log
- **File:** `bigdataAPI/Services/SP_BankUploadService.cs` (บรรทัด 1182–1185, 1203–1206)
- **Issue:** `catch { return null; }` ทำให้ failure ของ Cassandra/repository กลายเป็น field ว่างโดยไม่มี trace — debug production ยาก
- **Suggestion:** อย่างน้อย `catch (Exception ex)` แล้ว log (เช่น `ILogger` / pattern เดียวกับ repo ที่ `Console.WriteLine`) แล้วค่อย return `null`

### [suggestion] — `RequestNo` และ `BookNumber` ใน response ซ้ำกัน
- **File:** `bigdataAPI/Models/ResponseModels/SP_BankUploadResponse.cs` (บรรทัด 56–58), `bigdataAPI/Services/SP_BankUploadService.cs` (บรรทัด 375–377)
- **Issue:** ทั้งสอง field ถูก set จาก `bookNumber` ค่าเดียวกัน — client อาจสับสนว่าควรใช้ field ไหน (Phone upload ส่งแค่ `RequestNo`)
- **Suggestion:** ระบุใน API contract / frontend ว่า field หลักคืออะไร หรือส่ง field เดียวถ้า dashboard ไม่ต้องการทั้งคู่
